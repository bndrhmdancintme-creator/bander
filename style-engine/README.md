# Style Engine — B&W talking-head + color-washed glitch B-roll

A config-driven ffmpeg pipeline that reproduces the *mechanism* described in
the style brief — not the reference video itself:

- talking-head layer: constant grayscale + film grain, never changes color
- every B-roll cutaway gets its own color wash (sepia / green tint / cool
  blue / overexposed), independent of the caption color on top of it
- RGB-split "glitch" transition (shake → settle) at every cut, with 3 rapid
  burst clusters where several cuts land inside under a second
- bold Arabic caption, hard-cut in/out, color rotating yellow/red/white on
  its own rhythm — independent of the cut rhythm
- voice audio stays continuous under the cuts (only the picture is spliced)

Nothing here comes from the reference clip's pixels, audio, or watermark —
every filter chain was written from the technical description (grayscale
base + wash + rgbashift glitch + caption rotation), and the B-roll shipped
in `assets/broll_placeholders/` is procedurally generated by
`broll_generate.py` (noise, Conway's-life, a geq radial sweep, a soft
gradient, and a heavily blurred frame from *your own* clip) — swap those
for real footage whenever you have it.

## Requirements

```
apt-get install -y ffmpeg fonts-lemonada fonts-hosny-amiri
pip install --break-system-packages Pillow
```
(`Pillow` needs to be built with `libraqm` for correct Arabic shaping — the
apt-installed Pillow / the one in this container already has it. Run
`python3 -c "from PIL import features; print(features.check('raqm'))"` to
check; if it prints `False`, Arabic captions will render as disconnected
garbage no matter what font you use.)

## Quick start

```bash
# 1. generate placeholder B-roll sized to your footage (skip if you already
#    have real B-roll clips and just want to fill broll_sources below)
python3 broll_generate.py \
  --out-dir assets/broll_placeholders \
  --width 888 --height 1550 --fps 30 \
  --main-clip /path/to/your_talking_head.mp4

# 2. edit config.example.json (or copy it) -- at minimum:
#    - main_clip: path to your footage
#    - timeline: cut list covering 0..your clip's duration (seconds)
#    - captions: your actual 2-4 word phrases + timings (see below)

# 3. render
python3 apply_style.py --config config.example.json
```

## config.json schema

```jsonc
{
  "main_clip": "path/to/talking_head.mp4",
  "output": "output/final.mp4",
  "canvas": "888x1550",        // omit to use main_clip's native resolution
  "fps": 30,
  "glitch_default_ms": 200,     // base glitch-transition length; auto-boosted
                                 // ~25% on burst-cluster boundaries
  "sfx": true,                  // low-level noise "stab" under the voice at
                                 // every cut -- purely ffmpeg-generated, no
                                 // external audio
  "font_path": "/usr/share/fonts/opentype/lemonada/Lemonada-Bold.otf",
  "broll_dir": "assets/broll_placeholders",
  "broll_sources": { "archive": "archive.mp4", "crowd": "crowd.mp4", ... },
  "timeline": [
    {"start": 0.0, "end": 3.3, "source": "main"},
    {"start": 3.3, "end": 3.55, "source": "crowd"},
    ...
  ],
  "captions": [
    {"text": "وقفة قصيرة", "start": 0.3, "end": 1.8, "color": "yellow"},
    ...
  ]
}
```

- `timeline` entries must be contiguous and cover `[0, clip_duration]`
  exactly (each entry's `end` == the next entry's `start`).
- `source: "main"` pulls that time range straight out of `main_clip`
  (that's what keeps the voice-over continuous under the cuts).
- Any other `source` value must be a key in `broll_sources`; the wash
  (sepia/green_tint/sepia_light/cool_blue/overexposed) defaults per broll
  key (see `BROLL_DEFAULT_WASH` in `apply_style.py`) or can be overridden
  per timeline entry with `"wash": "..."`.
- To build a **burst cluster** (several very fast cuts in under a second,
  like the reference's 3.3–4.2s moment), just add several short
  (~0.2–0.35s) consecutive segments — the engine auto-detects any boundary
  next to a segment shorter than 0.5s and treats it as a burst (stronger
  glitch + a brief overexposed flash).
- `captions` timing is intentionally independent of the cut timeline —
  that's true to the brief ("caption rhythm != cut rhythm").

## config.example.json

This is the actual config used to render the sample against Bander's real
23s talking-head clip — a full working reference for the schema above, with
the exact cut list from the style brief (cuts every ~1.3–1.8s, 3 burst
clusters at ~3.3–4.2s / ~10.3–10.7s / ~15.0–15.7s) mapped onto that clip's
real 22.94s duration.

Two things in it are placeholders you should replace before reusing it on
different footage:

1. **`main_clip`** points at this session's upload path, which won't exist
   outside this container — point it at your own file.
2. **`captions`** text is generic filler (no real transcript was available
   when this was built — automatic speech-to-text was blocked by this
   environment's network policy, see below). Swap in phrases pulled from
   what you're actually saying at those timestamps.

## Known limitation: no auto-transcription in this session

The plan was to auto-generate caption text from the actual speech via
WhisperX/faster-whisper. `faster-whisper` installed fine, but it downloads
model weights from huggingface.co at runtime, and that host is blocked by
this environment's outbound network policy (403 at the gateway) — not a
flaky download, a hard block. So the captions in `config.example.json` are
placeholder phrases, not a transcript. If you run this somewhere with
HF Hub access, `whisperx-transcription` can give you word-level timestamps
to place real captions from.

## Why the glitch/B-roll pieces are re-rendered per run

Each timeline segment and each glitch transition is rendered to its own
temp `.mp4` in `.tmp_render/` (same codec/resolution/fps/pix_fmt across the
board) and stitched with the ffmpeg concat demuxer (`-c copy`, no
re-encode) — simpler and more robust than one giant filter graph, at the
cost of doing real work on every run. `--keep-temp` keeps `.tmp_render/`
around for debugging a specific segment's filter chain.

## File size note

Film grain is high-frequency noise that changes every frame, which is
exactly what H.264 compresses worst. The sample renders at CRF 23 and is
still tens of MB for 23 seconds — if you need a smaller file for direct
upload, either raise `-crf` in `apply_style.py`'s final encode or lower the
`noise=alls=...` values in `WASH_FILTERS`; either sacrifices some grain
texture for size.
